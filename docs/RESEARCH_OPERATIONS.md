# Research operations

Open a study's **Research Workspace** tab. Existing studies require explicit interviewer assignments and a screener before new face-to-face recruitment. Each screener question defines its allowed answers. Configure approved consent wording in the existing Consent tab. New F2F respondents start in training, submit a practice entry on their own phone, and are handed over only after the training and practice checks pass. Remote tutorial completion remains part of remote onboarding. Assign planned household visits with a date and location; the assigned interviewer records visited, no-answer, ineligible or recruited outcomes and notes from either portal.

Use Methodology & access to set participation requirements, minimum client bases, question-code mappings and comparable quantity units. A volume conversion applies to the selected quantity question; quantities in mixed units must be normalized before using that measure. Periods are UTC calendar days, Monday-start weeks or months. The current open period is included. Hybrid compliance counts period-summary entries. Real-time studies need a defined reporting cadence to have a compliance denominator. Practice, withdrawn/disqualified respondents, non-consented respondents, unresolved record QC, excluded records and unconfirmed AI answers are excluded from the appropriate analysis base. Optional explicit record approval can narrow the base further.

Incentives are configured per onboarding, completed-participation or final-validation milestone. Refresh eligibility after QC changes. A payment action records a payment already completed elsewhere; it does not transfer money. Record its real reference. Paid items remain auditable if later evidence changes. There is no automatic payment provider.

Research queries select supported segment, comparison, repeat, switching or approved-theme analyses. They are a bounded query interpreter, not unrestricted natural-language database access. Cross-tabs count distinct occasions even when a brand question repeats in product/member loops.

Reports use the same calculation module as client exports. Scheduled jobs run once a minute while the app is running, catch up after restarts and use unique snapshot IDs. Failed jobs retain their next run date and error. Snapshots and summaries require human approval. Alerts appear inside the research workspace. These jobs do not send respondent reminders or implement WhatsApp orchestration.

Questionnaire controls include scales, rankings, dates, times, deterministic per-respondent option rotation, UTC hour windows, and every-nth-occasion rules. Product/member loops create persisted question instances for configured labels so answers remain traceable to their item. Review wording and per-instance logic in the questionnaire builder after creating a loop. Ranking requires each configured option exactly once. Questions with time rules use the recorded occasion time, not sync time. Nth-occasion sequences can require review if two devices submit concurrently.

The native diary keeps copied media and queued packets in app-owned storage. Queued entries retry while the app is open and when it returns to the foreground. They survive app restarts; uninstalling the app or deleting its storage removes local unsynced data. First login and first questionnaire download require connectivity. The queue is not an OS background upload service. A failed or lost HTTP response can be retried with the same immutable submission identifier. Server ingestion stages records until their answers and media are complete. Legacy web forms remain online submission surfaces.

Client access, media, text and CSV grants are separate. Sharing media additionally requires respondent media consent. Local uploads now require authorization, as do requests that create private Azure read links. Azure links are time-limited bearer URLs and remain usable until their expiry. Withdrawal blocks future access immediately at the application, removes the participation from live analyses and returns released reports for review. After the configured retention period, an administrator can erase a due study participation by entering its respondent code. This does not delete a shared account/profile used by other studies. Retained audit and payment evidence must follow the organization's approved retention policy.

## Deployment and recovery

Run `node scripts/production-check.js` in the deployed environment; it only checks configuration and prints no secrets. Its results are not evidence of service connectivity. Enable managed MongoDB/Cosmos/Atlas point-in-time backups and private blob versioning using the deployment provider's supported configuration. Record the chosen retention period and responsible owner.

Before release, restore a managed database backup into an isolated database and recover a matching media version. Point an isolated application instance at the restored stores; verify study/respondent/record counts, replay a submission identifier, open an authorised recording, confirm denied client access, and compare one exported report to its approved snapshot. Record restore time, backup timestamp and the selected counts. Never point the drill at the live application database.

For the local development driver, `node scripts/local-backup.js backup SOURCE NEW_BACKUP` writes a private backup plus a SHA-256 manifest. `node scripts/local-backup.js restore BACKUP NEW_DATABASE` verifies the checksum and collection counts before creating a new database file. Both commands refuse to overwrite a file. This tool does not replace managed production backups and does not archive media.

Monitor application availability, failed research schedules, diary submissions stuck in ingesting, storage errors and audit failures. The Research Workspace shows schedule errors and internal compliance alerts. Set external uptime/process monitoring through your hosting provider. Production provisioning and a live restore drill require an available deployment account; they are not claimed by local tests.
