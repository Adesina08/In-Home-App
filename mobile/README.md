# INICIO Mobile — Native App Shell

This folder wraps the deployed INICIO web app in a real native app shell using
[Capacitor](https://capacitorjs.com/), so it can be published to the Google
Play Store and the Apple App Store instead of relying on "Add to Home
Screen."

## How this works (important — read this first)

This is **not** a rewrite. There is no second copy of the app's screens, no
new API, and no duplicated logic. The native app is a thin shell around a
single `WebView` that is configured to load your **live deployed web app
URL directly**, the same way the browser does today.

That means:

- Every feature works exactly as it does on the web today — respondent
  diary links, admin dashboard, questionnaire builder, skip logic, media
  uploads, everything — because it *is* the same web app, just opened
  inside a native container instead of a browser tab.
- When you ship a change to the web app (a new patch applied and deployed,
  same as always), the native app picks it up automatically the next time
  someone opens it. **You do not need to rebuild or resubmit the native app
  for ordinary feature/content changes.**
- You only need to rebuild and resubmit the native app when something
  about the *shell itself* changes: the app icon, the splash screen, the
  app name, the deployed URL it points at, or if a native-only capability
  is added later (e.g. push notifications via a Capacitor plugin).

## What's in this folder

- `capacitor.config.json` — the shell's configuration. `server.url` is the
  one setting that matters most (see Step 1 below).
- `android/` — a full native Android Studio/Gradle project, generated by
  Capacitor.
- `ios/` — a full native Xcode project, generated by Capacitor.
- `assets/` — the source icon/splash images used to generate every
  platform-specific icon and splash screen (reused from the web app's own
  PWA icons, so the native app and the "Add to Home Screen" PWA look
  identical).
- `www/` — a placeholder folder Capacitor's tooling requires to exist. It is
  never actually shown to users — `server.url` below overrides it.

## What could and couldn't be done in this build environment

This project was scaffolded in a sandboxed cloud environment with no access
to the Google Play Android SDK downloads or to Xcode (which only runs on
macOS). That means:

- ✅ Done here: the full Android and iOS native project structure, correct
  app ID/name, all generated app icons and splash screens for every
  required size/density, and this runbook.
- ❌ Not possible here, and not needed from here: actually compiling a
  signed `.aab`/`.apk` (Android) or `.ipa` (iOS). That step happens on
  your own machine using Android Studio (which downloads its own Android
  SDK automatically) and Xcode (Mac only) — see Steps 2 and 3 below. This
  is normal for Capacitor projects; it isn't a gap specific to this one.

## Step 1 — Point the app at your real deployed URL (required, one-time)

Open `capacitor.config.json` and replace the placeholder:

```json
"server": {
  "url": "https://REPLACE-WITH-YOUR-DEPLOYED-URL.azurewebsites.net",
  "cleartext": false
}
```

Change `url` to your real Azure App Service URL (the same `https://...
azurewebsites.net` address — or your custom domain, once B2 from the MVP
checklist is set up — that respondents and admins already use in the
browser today). Save the file, then from inside `mobile/` run:

```
npm install
npx cap sync
```

`cap sync` copies this config into both native projects. Re-run it any time
you change `capacitor.config.json`, the app icons, or add a Capacitor
plugin — but not for ordinary web-app deploys.

## Step 2 — Build & publish Android (Google Play)

You'll need [Android Studio](https://developer.android.com/studio)
installed (free; it installs its own Android SDK on first run — no manual
SDK setup needed).

1. `npm install` then `npx cap open android` (or open the `mobile/android`
   folder directly in Android Studio).
2. Let Gradle sync finish (first time can take a few minutes).
3. **Build → Generate Signed Bundle / APK** → choose **Android App Bundle
   (.aab)** (Play Store requires this format for new apps).
4. Create a new signing key if you don't have one yet (Android Studio walks
   you through this) and **keep that keystore file and its passwords safe
   and backed up** — Google Play permanently ties your app to it; losing it
   means you can never update the app again under the same listing.
5. Create a [Google Play Console](https://play.google.com/console) developer
   account (one-time $25 fee), create a new app listing, fill in the store
   listing (description, screenshots, privacy policy URL, content rating
   questionnaire), and upload the `.aab` under **Production** (or
   **Internal testing** first, which is recommended for your pilot).
6. Submit for review. Google's review typically takes a few hours to a
   couple of days for a new app.

## Step 3 — Build & publish iOS (Apple App Store)

Requires a Mac with [Xcode](https://developer.apple.com/xcode/) installed,
and an active [Apple Developer Program](https://developer.apple.com/programs/)
membership ($99/year).

1. On the Mac, install [CocoaPods](https://cocoapods.org/) if not already
   installed: `sudo gem install cocoapods`.
2. Copy this whole `mobile/` folder to the Mac (or `git clone` the repo
   there), run `npm install`, then `cd ios/App && pod install`.
3. `npx cap open ios` (from `mobile/`) opens the project in Xcode.
4. In Xcode: select the `App` target → **Signing & Capabilities** → sign in
   with your Apple Developer account and let Xcode manage signing
   automatically.
5. **Product → Archive**, then use the Organizer window's **Distribute App**
   flow to upload the build to **App Store Connect**.
6. In [App Store Connect](https://appstoreconnect.apple.com/), create the
   app listing (description, screenshots, privacy policy URL, age rating),
   attach the uploaded build, and submit for review. Apple's review
   typically takes 1–3 days.

## Updating the app icon or splash screen later

Replace the images in `mobile/assets/` (keep the same filenames:
`icon-only.png`, `icon-foreground.png`, `splash.png`, `splash-dark.png`),
then from `mobile/` run:

```
npx capacitor-assets generate
npx cap sync
```

This regenerates every platform-specific size automatically. You'll need to
rebuild and resubmit the app in both stores after this, since it's a shell
change (see "How this works" above).

## FAQ

**Do respondents' personal diary links still work the same way?**
Yes — the app opens the exact same web app over HTTPS, so links, sessions,
and cookies all behave identically to opening the link in a mobile browser.

**Does this replace the PWA / "Add to Home Screen" option?**
No, both can coexist. The `/get-app` page can continue to offer the PWA
install path for anyone who doesn't want to install from a store, while the
Play Store / App Store listings (once live) offer this native shell as an
alternative for people who prefer installing from a store.

**Something changed on the web app and it's not showing up in the native
app.**
Force-close and reopen the app (WebViews cache like a browser). If the
issue persists, check that `capacitor.config.json`'s `server.url` still
points at the correct, currently-deployed URL.
